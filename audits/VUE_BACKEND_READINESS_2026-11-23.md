## 2. HTML ↔ Vue
- `index.html` является главным HTML-legacy приложением (7.6 МБ); Vue — компоненты из `frontend/knowledge-map/*.vue`, собранные в `assets/ui/knowledge-map.js`.
- `frontend/knowledge-map/mount.js` регистрирует UI-экраны и создаёт Vue-приложение на переданном хосте.
- Доказанный дефект: при повторном `mountView` обновлялась только модель, в то время как render замыкал старые `actions` и `view`. Исправлено в PR #130: все три поля в реактивном состоянии.
- Отдельная регрессия Playwright проверяет новую модель, новые callbacks, смену Vue-компонента в одном host и удаление host.
- Остаётся: независимая инвентаризация обработчиков в 7.6 МБ `index.html`, измерение покрытия реальных UI-маршрутов и e2e на мобильной/настольной ширине.

## 3. Сохранение и награды
- Автотесты Stage22/24/25/26 зелёные. Скрипт `audits/vue_public_upgrade_browser.cjs` проверяет отдельные профили, историю, однократность завершения попыток, F5 в офлайне и возврат к черновику при переходах между сборками.
- Нельзя переносить начисление XP/монет на сервер до определения одного идентификатора события попытки и инварианта `rewardGrantedOnce`. Повторная доставка события после офлайна и F5 должна быть идемпотентной.
- Входные данные для будущего backend: профиль, идентификатор попытки, тип тренажёра, snapshot конфигурации, ответы/счёт, статус (draft/finished), локальный seq, версия схемы; сервер возвращает подтверждение и авторитетный баланс. UI не показывает кнопку «Сохранить на сервере».

## 4. Offline / PWA
- `sw.js` хранит версионированный snapshot HTML и набор проверяемых SHA-256 скриптов, включая `assets/ui/knowledge-map.js`.
- `audits/g7_stage12_sync_pwa.py --check` проверяет соответствие snapshot-фингерпринтов текущим HTML и скриптам.
- **Блокер выпуска PR #130:** изменение `.vue`/`mount.js` само по себе не меняет уже закоммиченный `assets/ui/knowledge-map.js`. Перед публикацией требуется собрать bundle, обновить ссылку версии в HTML, cache version/hash SW и повторно прогнать upgrade/offline тесты. Нельзя выпускать источник без синхронной сборки.
- Ранее успешно проверены офлайн-открытие классов, магазина и сохранение баланса (Stage28), но сетевой конфликт между двумя устройствами и очередь повторной доставки событий пока не проверены.

## 5. Подготовка backend
- В дереве текущей ветки GitHub отсутствует отдельный каталог backend/API; здесь пока frontend-приложение. Не выдавать проект за уже перенесённый на сервер.
- Устойчивое разделение: локально — рендеринг, ввод, проверка промежуточных шагов, offline drafts; сервер — учётная запись/класс/тариф, подтверждённые итоги, лимиты доступа, кошелёк/покупки и защита от дублей.
- Требуемые контракты: `GET /session`, `POST /attempts/sync` (batch с idempotency key), `GET /profiles/{id}/progress`, `POST /economy/transactions`; эти маршруты **предложены для проектирования, не существуют в текущем дереве**.
- Нужны миграции локальных профилей, конфликты между устройствами, offline outbox с retry, merge policy, постоянные server IDs и versioned schema.

## Выходные условия перед production
1. Обновлённый скомпилированный Vue bundle, HTML и SW — одной согласованной версии.
2. CI e2e: реальный роутинг, клавиатура, F5 offline, прохождение, повторный запуск, начисление наград ровно один раз, возврат к плану.
3. Ручная проверка на Android и desktop.
4. Только после этого — явное решение о релизе.
