# МатКвест: контракт локальной работы и синхронизации с backend (проект v1)

Дата: 23.11.2026. Статус: **проект контракта, не реализованный API**.
Репозиторий GitHub содержит HTML/Vue/PWA и локальное хранилище; существование backend-роутов из документа не предполагается.

## Цель и граница доверия

- В браузере: задания, клавиатура, обратная связь, черновик, локальный прогресс, офлайн-запуск, очередь отправки.
- На сервере: аутентификация, права репетитора/ученика, тариф/квоты, окончательные результаты, экономика, транзакции, защита от дублей.
- Никакой кнопки «Сохранить на сервере»: `IndexedDB` сохраняет автоматически, синхронизация выполняется при появлении сети и открытии приложения.
- Отдельно не пересчитывать каждое нажатие на сервере: клиент работает мгновенно, сервер проверяет итоговое событие и применяет только разрешённые начисления.

## Канонические идентификаторы

- `profile_id`: неизменяемый UUID пользователя/ученика, не имя профиля; импорт старого профиля получает явное отображение local -> server.
- `attempt_id`: UUID создаётся при старте и не меняется после F5, повторной отправки или возобновления.
- `event_id`: UUID создаётся ровно один раз при локальной фиксации события; один и тот же `event_id` повторно передаётся при retry.
- `seq`: возрастающий номер локального события внутри профиля; применяется для диагностики конфликтов, не заменяет event_id.
- `schema_version`: версия сериализации черновика и сетевого события; API должен допускать согласованную миграцию.

## Основные сообщения

`POST /api/v1/attempts/sync` — пакет событий с идемпотентностью.

Пример входа (примерные поля, **не существующий endpoint**):

```json
{
  "schema_version": 1,
  "device_id": "device-uuid",
  "events": [
    {
      "event_id": "event-uuid",
      "profile_id": "server-profile-uuid",
      "attempt_id": "attempt-uuid",
      "seq": 105,
      "kind": "attempt_finished",
      "course_topic_id": "g4:table",
      "stage_index": 0,
      "started_at": "2026-11-23T08:00:00Z",
      "finished_at": "2026-11-23T08:10:00Z",
      "result": { "correct": 8, "total": 10, "skipped": 0, "corrected": 2 },
      "content_revision": "catalog-revision"
    }
  ]
}
```

Ответ возвращает подтверждение каждому `event_id`, `server_revision` профиля, серверный статус попытки и авторитетные XP/монеты. Повтор идентичного события возвращает прежний результат без второго начисления. Совпадающий `event_id` с иным payload — конфликт, а не новая операция.

## Обязательные инварианты backend

1. Завершение одной попытки применяется **один раз** независимо от F5, количества HTTP retry и нескольких устройств.
2. Начисление XP/монет и запись законченной попытки совершаются в одной транзакции.
3. Новое устройство не может изменить историю старой попытки повторной отправкой.
4. Покупки и траты монет подчиняются отдельному ledger c `transaction_id` и уникальным ключом идемпотентности.
5. Проверка платного доступа, тарифов и лимитов — серверная; локальное отображение прав лишь UX-кеш.
6. Недействительные/не принадлежащие аккаунту profile_id отвергаются без побочного действия.
7. `attempt_finished` неизменяем: последующие пользовательские исправления создают новую попытку, а не меняют старую.

В PostgreSQL нужны уникальные ограничения на `(profile_id, event_id)` и на применённое завершение `(profile_id, attempt_id, event_kind)`; денежные изменения — отдельная атомарная запись в журнале транзакций.

## Локальная очередь и восстановление

- Локальная транзакция записывает одновременно черновик/итог, изменение локального отображения и unsent-event в outbox. Если запись не удалась, попытка не считается отправленной.
- После reconnect посылать небольшие пакеты, с exponential backoff; `ack` удаляет только соответствующий outbox record, не локальную историю.
- `offline` и `unconfirmed` события остаются видимыми локально; итоговое серверное состояние сверяется автоматически при reconnect.
- При конфликте сервер отдаёт структурированную причину и авторитетную ревизию. Не подменять баланс молча.
- Обновление service worker не должно терять outbox и локальные черновики; UI обновляется только после защищённого сохранения.
- Две активные незаконченные попытки одного типа с разных устройств не объединять автоматически; сохранять отдельные UUID.

## Квоты Free и офлайн

Для квоты «10 бесплатных тренировок / 24 ч» нужно заранее определить политику офлайн-допуска: серверная история остаётся источником истины, но UX не может внезапно блокировать сохранённую работу при reconnect. Локальный счётчик ограничивает офлайн-возможность, сервер подтверждает доступные результаты после связи. Поведение при превышении квоты должно иметь заранее прописанный сценарий, без потери ответов.

## Приёмочные тесты перед подключением UI

- Same event 100 retries -> 1 attempt, 1 reward.
- Crash after DB commit before HTTP response -> replay returns previous acknowledgement, no extra coins.
- Offline F5 -> same attempt_id and unsent event_id; after reconnect profile/history correct.
- Two devices submit same attempt_id -> server settles once.
- Invalid profile and forged balance -> rejected; wallet unchanged.
- Imported local profiles remain distinct and linked to correct owner.
- Offline draft survives PWA version upgrade and sync begins automatically.
- Backend unavailable -> local training works; no fabricated «сохранено на сервере».

## Предварительный порядок внедрения

1. Согласовать DTO и миграцию старых `profileId` и `attemptId`.
2. Написать независимый тест транзакционного идемпотентного ledger на PostgreSQL.
3. Реализовать outbox на фронтенде за адаптером, не переписывая Vue-компоненты.
4. Добавить e2e online → offline → F5 → online и две вкладки/два устройства.
5. Провести приватный пилот без включения production-начислений.
